# RASP: проверки среды выполнения

RASP (runtime application self-protection) — часть библиотеки, которая во время работы приложения ищет признаки взломанной или враждебной среды: root, средства перехвата вызовов (Frida, Xposed), отладчик, эмулятор, чужую подпись APK. Документ перечисляет все проверки и описывает, что библиотека делает с находками. Он составлен по коду: `api/RaspPolicy.kt`, пакет `rasp/`, `devicetrust-native/`.

Как RASP выглядит со стороны приложения — в [`API.md`, раздел 10](API.md#10-rasp-с-точки-зрения-приложения); как он связан с остальными частями библиотеки — в [`ARCHITECTURE.md`](ARCHITECTURE.md).

## 1. Место RASP в защите

RASP — дополнительный слой. На устройстве с root его можно обойти целиком: подменить результаты проверок, заглушить реакцию, не дать отправить сообщение шлюзу. Основной контроль — проверка аттестации ключа на шлюзе при регистрации и при каждом продлении сертификата: состояние загрузчика, целостность системы, подпись приложения и уровень защиты ключа шлюз узнаёт от аппаратного хранилища, а не от приложения.

RASP нужен для двух вещей: быстро стереть секреты на устройстве, когда признаки взлома видны, и дать шлюзу сведения о парке устройств.

Термины:

| Термин | Значение |
|---|---|
| Проход | одно выполнение всех проверок |
| Находка | сработавшая проверка: идентификатор, реакция и подробность (`RaspFinding(id, reaction, detail)`) |
| Реакция | что библиотека делает с находкой: `BLOCK`, `REPORT` или `IGNORE` |
| BLOCK | стереть ключи устройства и Vault, перейти в состояние `Blocked`, сообщить шлюзу. Необратимо |
| REPORT | отправить шлюзу сообщение; для пользователя ничего не меняется |
| Двойная проверка | проверка, реализованная дважды — на Kotlin и на C — с одинаковыми входными данными. Расхождение результатов само является находкой |

## 2. Когда выполняется проход

| Повод | Где в коде |
|---|---|
| После `DeviceTrust.init`, сразу за сверкой состояния | `DeviceTrust.init` |
| При выходе приложения на передний план и затем каждые `raspIntervalForeground` (по умолчанию 5 минут), пока оно там | `DeviceTrust.ForegroundRasp` |
| В начале предпроверки, а значит и регистрации | `Precheck.run` |
| Перед каждым продлением и восстановлением сертификата | `CertManager.renew`, `CertManager.recover` |
| По вызову `DeviceTrust.checkIntegrity()` | `DeviceTrustCore.checkIntegrity` |

Каждый проход, откуда бы он ни был запущен, идёт через одну точку (`RaspScanner` в `DeviceTrust.init`), которая после него: обновляет разрешение на выдачу секретов Vault ([раздел 5](#5-integritygate-секреты-только-после-проверки)), учитывает проход в сводке ([раздел 6](#6-сводка-rasp-при-продлении)) и ставит находки с реакцией REPORT в очередь на отправку.

## 3. Проверки

Идентификаторы — константы объекта `RaspCheck`; реакции по умолчанию — `RaspCheck.DEFAULTS`.

| Идентификатор | Что обнаруживает | Реализация | Реакция по умолчанию | Второй проход перед BLOCK |
|---|---|---|---|---|
| `ROOT_SU` | исполняемый файл `su` | Kotlin и C (двойная) | BLOCK | да |
| `ROOT_MAGISK` | следы Magisk, KernelSU, APatch | C | BLOCK | да |
| `ROOT_MANAGER_PKG` | установленное приложение управления root | Kotlin | REPORT | — |
| `ROOT_PROPS` | системные свойства отладочной прошивки | C | BLOCK | да |
| `ROOT_TEST_KEYS` | прошивка, подписанная тестовыми ключами | Kotlin и C (независимо) | REPORT | — |
| `HOOK_FRIDA_MAPS` | библиотеки и потоки Frida в процессе | C | BLOCK | да |
| `HOOK_FRIDA_PORT` | сервер Frida на локальном порту | C | BLOCK | да |
| `HOOK_XPOSED` | среда Xposed или LSPosed | Kotlin | BLOCK | да |
| `HOOK_TAMPER` | расхождение Kotlin- и C-проверок или недоступность C-части | сравнение | REPORT | да |
| `DEBUGGER` | присоединённый отладчик | Kotlin и C (двойная) плюс Kotlin | BLOCK | да |
| `APK_SIGNATURE` | APK подписан не ожидаемым сертификатом | Kotlin и C (двойная) | BLOCK | нет |
| `APP_DEBUGGABLE` | приложение собрано отладочным | Kotlin | BLOCK | нет |
| `EMULATOR` | эмулятор | Kotlin и C (двойная) | BLOCK | да |
| `KEYSTORE_SOFTWARE` | ключи Keystore не защищены аппаратно | Kotlin | BLOCK | нет |
| `DEV_OPTIONS` | включён режим разработчика | Kotlin | REPORT | — |
| `ADB_ENABLED` | включена отладка по USB | Kotlin | REPORT | — |
| `NO_SCREEN_LOCK` | не установлена блокировка экрана | Kotlin | REPORT | — |

Прочерк в последнем столбце означает, что проверка по умолчанию не блокирует. Если политика поднимет её реакцию до BLOCK, блокировка наступит с первого прохода.

### Что именно проверяется

| Идентификатор | Входные данные | Подробность находки |
|---|---|---|
| `ROOT_SU` | Вызов `stat` для путей `/system/bin/su`, `/system/xbin/su`, `/sbin/su`, `/su/bin/su`, `/data/local/su`, `/data/local/bin/su`, `/data/local/xbin/su`, `/system/sd/xbin/su`, `/vendor/bin/su`, `/product/bin/su`, `/odm/bin/su`, `/debug_ramdisk/su`, затем `<каталог>/su` для каждого каталога из переменной окружения `PATH` | найденный путь |
| `ROOT_MAGISK` | Существование `/sbin/.magisk` или `/debug_ramdisk/.magisk`; в `/proc/self/mountinfo` — подстроки `magisk` и `/data/adb/modules`, а также отдельные поля `KSU` и `APatch` (источник монтирования у KernelSU и APatch) | путь или `mountinfo:<признак>` |
| `ROOT_MANAGER_PKG` | Установлен ли один из пакетов: `com.topjohnwu.magisk`, `io.github.vvb2060.magisk`, `io.github.huskydg.magisk`, `me.weishu.kernelsu`, `me.bmax.apatch`, `eu.chainfire.supersu`, `com.koushikdutta.superuser`, `com.noshufou.android.su`. Эти же пакеты перечислены в блоке `<queries>` манифеста библиотеки, иначе система их не покажет | имя пакета; по одной находке на пакет |
| `ROOT_PROPS` | Системные свойства `ro.debuggable` равно `1` или `ro.secure` равно `0` | `ro.debuggable=1` или `ro.secure=0` |
| `ROOT_TEST_KEYS` | Kotlin: `Build.TAGS` содержит `test-keys`. C: свойство `ro.build.tags` содержит `test-keys`. Некоторые заводские прошивки, проходящие аттестацию, несут этот признак, поэтому он только сообщается | `Build.TAGS=test-keys`; `native:ro.build.tags=test-keys` |
| `HOOK_FRIDA_MAPS` | В `/proc/self/maps` — подстроки `frida`, `gum-js`, `libgadget.so`; в именах потоков процесса (`/proc/self/task/<номер>/comm`) — `gum-js-loop`, `pool-frida`, `frida` | `maps:<признак>` или `thread:<признак>` |
| `HOOK_FRIDA_PORT` | Соединение с `127.0.0.1` на порты 27042 и 27043; отправляется начало рукопожатия D-Bus, и ответ `REJECTED` означает сервер Frida | `port=<номер>` |
| `HOOK_XPOSED` | Загружаются ли классы `de.robv.android.xposed.XposedBridge`, `de.robv.android.xposed.XposedHelpers`, `org.lsposed.lspd.core.Main`; есть ли в текущем стеке вызовов классы с `de.robv.android.xposed`, `org.lsposed`, `LSPHooker`, `EdHooker` в имени | имя класса |
| `DEBUGGER` | Двойная часть: поле `TracerPid` в `/proc/self/status` не равно нулю. Только Kotlin: `Debug.isDebuggerConnected()` или `Debug.waitingForDebugger()` | `tracer=<номер процесса>`; `jdwp` |
| `APK_SIGNATURE` | Kotlin: каждый действующий сертификат подписи, который сообщает `PackageManager`, должен входить в `expectedSigningDigests`. C: то же, но сертификаты читаются из блока подписи установленного файла `base.apk` (схемы подписи v2, v3, v3.1), путь к которому берётся из `/proc/self/maps`. Проверка выполняется, только если `expectedSigningDigests` не пуст | `no signers` или `unexpected=<SHA-256>` |
| `APP_DEBUGGABLE` | Флаг `FLAG_DEBUGGABLE` приложения | — |
| `EMULATOR` | `Build.HARDWARE` (в C — свойство `ro.hardware`) равно `goldfish`, `ranchu` или `vbox86`; `Build.FINGERPRINT` (`ro.build.fingerprint`) начинается с `generic` либо содержит `emulator` или `sdk_gphone`; существует один из путей `/dev/qemu_pipe`, `/dev/goldfish_pipe`, `/dev/socket/qemud`, `/sys/qemu_trace`, `/system/bin/qemu-props`, `/system/lib/libc_malloc_debug_qemu.so` | `hardware=…`, `fingerprint=…` или путь |
| `KEYSTORE_SOFTWARE` | Уровень защиты Keystore, измеренный предпроверкой и сохранённый в `precheck.properties`, не `TRUSTED_ENVIRONMENT` и не `STRONGBOX`. Пока предпроверка ни разу не выполнялась, проверка ничего не находит | название уровня |
| `DEV_OPTIONS` | `Settings.Global.DEVELOPMENT_SETTINGS_ENABLED` | — |
| `ADB_ENABLED` | `Settings.Global.ADB_ENABLED` | — |
| `NO_SCREEN_LOCK` | `KeyguardManager.isDeviceSecure` возвращает `false` | — |

### Три исхода проверки

Проверка, которая обращается к файлу, имеет три исхода (`ProbeState`): «найдено», «чисто» и «доступ запрещён» (ошибки `EACCES` и `EPERM`). Запрет доступа — отдельный исход и находкой не считается: на обычном телефоне система запрещает приложению читать многие пути. Если среди нескольких путей один найден, исход — «найдено»; иначе, если хотя бы к одному доступ запрещён, — «доступ запрещён».

### Сравнение двух реализаций и `HOOK_TAMPER`

Проверки `ROOT_SU`, `DEBUGGER` (часть с `TracerPid`), `EMULATOR` и `APK_SIGNATURE` выполняются и на Kotlin, и на C с одними и теми же путями, свойствами и системными вызовами. Перехват, который обманывает одну реализацию, но не другую, приводит к расхождению.

`RaspEngine.evaluate` объединяет результаты так:

| Ситуация | Находка |
|---|---|
| Kotlin-проверка дала «найдено» | находка этой проверки с её подробностью |
| C-проверка дала «найдено», а Kotlin-проверки с таким идентификатором нет или она не дала «найдено» | находка этой проверки с подробностью `native:<подробность>` |
| Исходы двойной проверки на Kotlin и на C различаются | `HOOK_TAMPER` с подробностью `<идентификатор> kotlin=<исход> native=<исход>` |
| C-часть не вернула строку для двойной проверки | `HOOK_TAMPER` с подробностью `<идентификатор> missing in native` |
| C-библиотека не загрузилась или вызов завершился ошибкой | `HOOK_TAMPER` с подробностью `native unavailable` |
| Ответ C-части короче кода аутентичности, не прошёл проверку кода или не разбирается | `HOOK_TAMPER` с подробностью `short`, `jni hmac` или `malformed` |

Одинаковые находки (тот же идентификатор и та же подробность) в одном проходе объединяются.

Списки путей и признаков двойных проверок записаны дважды — в `rasp/Checks.kt` и в `devicetrust-native/strings.txt`. Тест `ListsInSyncTest` не даёт им разойтись: расхождение списков дало бы `HOOK_TAMPER` на каждом устройстве.

## 4. Реакции

### 4.1 Политика и тип сборки

Реакция на находку определяется так (`EffectivePolicy`):

1. Берётся реакция по умолчанию из `RaspCheck.DEFAULTS`. Для идентификатора, которого там нет, — REPORT.
2. Применяются переопределения из `DeviceTrustConfig.raspPolicy`. Усиление реакции действует всегда. Ослабление действует только в пилотной и отладочной сборках; в выпускаемой оно игнорируется, а в журнал записывается `rasp_policy_downgrade_ignored`.
3. Находка с реакцией `IGNORE` отбрасывается.
4. В пробном режиме ([раздел 4.2](#42-пробный-режим)) реакция BLOCK заменяется на REPORT.

Действующий тип сборки библиотека определяет сама, не полагаясь на заявленный `buildKind`:

| Приложение отладочное | Заявлен `buildKind` | `versionCode` пилотный | Действующий тип |
|---|---|---|---|
| да | любой | любой | заявленный |
| нет | `PILOT` | да | `PILOT` |
| нет | `PILOT` | нет | `RELEASE` |
| нет | `RELEASE` или `DEBUG` | любой | `RELEASE` |

«Пилотный `versionCode`» определяет функция `DeviceTrustConfig.pilotVersionCode`; по умолчанию это номера, у которых две последние цифры от 90 до 99.

### 4.2 Пробный режим

При `raspDryRun = true` в пилотной или отладочной сборке каждая находка с реакцией BLOCK превращается в находку с реакцией REPORT и подробностью `dryRun;BLOCK;<исходная подробность>`. Устройство не блокируется, Vault остаётся открытым, а шлюз получает сообщение о том, что блокировка произошла бы. Режим нужен, чтобы на пилоте измерить долю ложных срабатываний. В выпускаемой сборке параметр игнорируется.

### 4.3 Второй проход

Реакция BLOCK необратима, а часть проверок эвристические: один снимок `/proc` может дать случайное совпадение. Поэтому, если первый проход дал блокирующую находку одной из проверок `ROOT_SU`, `ROOT_MAGISK`, `ROOT_PROPS`, `HOOK_FRIDA_MAPS`, `HOOK_FRIDA_PORT`, `HOOK_XPOSED`, `HOOK_TAMPER`, `DEBUGGER`, `EMULATOR`, библиотека немедленно выполняет второй проход (`RaspEngine.confirmed`).

- Проверка снова дала блокирующую находку — реакция BLOCK остаётся.
- Не дала — находка первого прохода превращается в REPORT с подробностью `unconfirmed;BLOCK;<исходная подробность>`.

Проверки `APK_SIGNATURE`, `APP_DEBUGGABLE` и `KEYSTORE_SOFTWARE` не могут дать случайный результат и блокируют с первого прохода.

### 4.4 Реакция BLOCK

Блокировку выполняет `CertManager.raspBlock` в строгом порядке:

1. Собрать сообщение `BLOCK` с перечнем находок, подписать его ключом устройства, пока ключ существует, и записать в очередь на диске.
2. Записать в `state.json` фазу `BLOCKED` с причиной `RASP`.
3. Удалить ключи устройства, ключи и файлы Vault, файлы сертификатов; закрыть соединения.
4. Отправить приложению событие `TrustEvent.Blocked(RASP)`.
5. Запустить фоновую отправку очереди.

Сбой между шагами закрывается при следующем запуске: увидев фазу `BLOCKED`, библиотека повторяет стирание и событие. Устройство, которое уже заблокировано, повторно не стирается и второе сообщение не создаёт. Подробности, включая доставку сообщения, — в [`ARCHITECTURE.md`, раздел 6.6](ARCHITECTURE.md#66-блокировка-block).

### 4.5 Реакция REPORT и ограничение частоты

Находки с реакцией REPORT после каждого прохода попадают в очередь (`AlertQueue.addReports`). Ограничения задаёт `DeviceTrustConfig.reportRateLimit`:

| Параметр `ReportLimit` | По умолчанию | Действие |
|---|---|---|
| `perCheckWindow` | 24 часа | находка с той же парой (идентификатор, подробность) ставится в очередь не чаще одного раза за окно |
| `queue` | 100 | наибольшее число находок, ожидающих отправки; при переполнении отбрасываются самые старые |
| `batch` | 20 | наибольшее число находок в одном сообщении |

Подробность входит в ключ ограничения: `ROOT_SU` с путём `/system/bin/su` и `ROOT_SU` с пометкой `dryRun;BLOCK;/system/bin/su` считаются разными находками. Отметка времени ставится в момент постановки в очередь, а не в момент доставки.

Перед отправкой находки собираются в сообщения `REPORT` и подписываются ключом устройства. Если ключа нет, сообщение уходит без подписи вместе с cookie сессии Kratos.

### 4.6 Формат сообщения шлюзу

Сообщения всех трёх видов отправляются запросом `POST /v1/device/alert` на адрес `enrollBaseUrl` (S3 §5.7). Тело запроса:

```json
{"payload": "<base64>", "sig": "<base64 или null>", "certSerial": "<серийный номер или null>"}
```

`payload` — байты JSON:

```json
{"v":1,"kind":"BLOCK","deviceId":"…","certSerial":"…","ts":"2026-11-08T10:00:00Z","appVersionCode":10300,"checks":[{"id":"ROOT_SU","detail":"/system/bin/su"}]}
```

`kind` — `BLOCK`, `REPORT` или `UNENROLL`; подробность каждой находки обрезается до 200 символов. `sig` — подпись ECDSA с SHA-256 над байтами `payload` ключом действующего сертификата; шлюз проверяет её и для истёкшего сертификата. Если ключа устройства нет, `deviceId`, `certSerial` и `sig` равны `null`.

## 5. IntegrityGate: секреты только после проверки

`IntegrityGate` не даёт Vault расшифровывать и шифровать, пока среда не проверена. У него три положения:

| Положение | Когда | Операции Vault |
|---|---|---|
| ожидание | с запуска процесса до конца первого прохода | ждут до 20 секунд; если проход не закончился — `VaultException.Locked` |
| открыто | последний проход разрешил выдачу секретов | выполняются |
| закрыто | последний проход не разрешил | `VaultException.Locked` |

Проход разрешает выдачу секретов (`RaspEngine.allowsSecrets`), когда одновременно:

- в нём нет ни одной находки с реакцией BLOCK;
- C-часть ответила и её ответ прошёл проверку — либо действующий тип сборки не `RELEASE`.

Второе условие закрывает самый дешёвый обход: сломать загрузку `libwolpdt.so`, чтобы отключить половину проверок. Сама находка при этом остаётся `HOOK_TAMPER` с реакцией REPORT, устройство не блокируется, но в выпускаемой сборке секреты не выдаются. Проход, который не смог выполниться из-за исключения, закрывает Vault.

Закрытое положение — не стирание. Стирает реакция BLOCK; `IntegrityGate` лишь гарантирует, что между обнаружением и стиранием, а также при неработающих проверках ничего не будет расшифровано. Положение обновляется после каждого прохода, поэтому Vault снова открывается, как только очередной проход оказывается чистым.

## 6. Сводка RASP при продлении

Без сводки шлюз узнаёт о работе RASP только из сообщений о находках, и молчание устройства неотличимо от ситуации, когда проверки не выполняются. Поэтому библиотека считает проходы и вместе с каждым продлением и восстановлением сертификата отправляет шлюзу сводку (S2 §6.3, S3 §5.4a).

Сводка — байты JSON такого вида:

```json
{"v":1,"native":true,"passes":17,"nativeFail":0,"since":"2026-11-08T10:00:00Z","findings":["ADB_ENABLED","DEV_OPTIONS"]}
```

| Поле | Значение |
|---|---|
| `passes` | число проходов с прошлого успешного продления или с регистрации |
| `nativeFail` | в скольких из них C-часть не ответила или её ответ не прошёл проверку |
| `native` | `true`, если проходы были и C-часть отработала в каждом |
| `since` | с какого момента ведётся счёт; поля нет, если ещё ничего не считалось |
| `findings` | идентификаторы находок за это время, отсортированные, без подробностей; не больше 32 |

Правила (`RaspSummaryStore`):

- Счётчики хранятся в файле `rasp-summary.json`, потому что между двумя продлениями процесс запускается много раз. Они переживают блокировку и отвязку и сбрасываются при новой регистрации. Потеря или порча файла только начинает счёт заново; сбой записи счётчика не делает проход неудачным.
- Сводка отправляется только шлюзу, который в ответе на запрос одноразового числа объявил `"features":["raspSummary"]`. Вместе с ней используется вторая версия подписи `continuitySig`, которая покрывает SHA-256 байтов сводки; см. [`ARCHITECTURE.md`, раздел 6.3](ARCHITECTURE.md#63-продление). Шлюзу, который поддержку не объявил, запросы идут в прежнем виде.
- Байты сводки подписываются как есть, без приведения к каноническому виду.
- После успешного ответа шлюза из счётчиков вычитается отправленное. Проходы, выполненные между подготовкой сводки и ответом, остаются учтёнными; вместе с ними остаются и идентификаторы находок. При отказе шлюза или потере ответа счётчики не меняются.
- Каждый счётчик ограничен значением 1 000 000.

Сводку подписывает ключ устройства, а не доверенная среда, поэтому приложение под полным контролем атакующего может прислать «чисто». Сводка закрывает дешёвые обходы и показывает картину по парку устройств.

## 7. Защита native-части

C-часть (`libwolpdt.so`) сама решений не принимает: она возвращает результаты проверок, а реакцию выбирает Kotlin-код. Её защищают следующие меры:

| Мера | Как сделано |
|---|---|
| Результат нельзя просто подменить | Kotlin-код при создании `NativeChecks` генерирует случайный 32-байтный ключ процесса и передаёт его в каждый вызов. C-часть возвращает строки результата и их HMAC-SHA256 на этом ключе; Kotlin-код проверяет код до разбора. Перехват, который заменяет возвращаемое значение, даёт `HOOK_TAMPER` |
| Строки проверок не видны в файле | Все строковые константы записаны в `devicetrust-native/strings.txt`. Задача `:devicetrust:generateNativeStrings` превращает файл в заголовок `wolpdt_strings.h`, где каждая строка зашифрована своим потоком ключа. Во время работы строка расшифровывается в буфер на стеке и стирается при выходе из области видимости (макрос `DEC` в `obf.h`) |
| Шифрование строк проверяется при сборке | Задача `:devicetrust:checkNativeStrings` завершается ошибкой, если какая-либо строка длиной от 4 байтов читается в `libwolpdt.so` из выпускаемого AAR |
| Наружу не видно имён функций | Библиотека собирается со скрытой видимостью символов; экспортируется только `JNI_OnLoad`, а функция прохода регистрируется вызовом `RegisterNatives`. Правило в `consumer-rules.pro` сохраняет от R8 класс `NativeRasp`, к которому она привязывается |
| Сертификаты подписи читаются в обход `PackageManager` | `apksig.c` сам разбирает блок подписи APK, поэтому перехват в `PackageManager` приводит к расхождению с Kotlin-проверкой |

Шифрование строк — это запутывание, а не секретность: ключи находятся в том же файле. Оно убирает список проверок из вывода утилиты `strings` и затрудняет простые правки по шаблону байтов.

Формат ответа C-части: строки вида `<идентификатор>|<исход>|<подробность>`, где исход — `F` (найдено), `C` (чисто) или `D` (доступ запрещён), и после них 32 байта кода аутентичности.

## 8. Известные ограничения

- Проверки не запускались на устройстве с root и с Frida: неизвестно, какие из них срабатывают на реальном взломанном телефоне и какие дают ложные срабатывания на редких прошивках.
- Вердикт и реакция находятся в Kotlin-коде. Перехват, установленный до первого прохода, может отключить их целиком.
- `HOOK_TAMPER` по умолчанию только сообщается. Решение о блокировке будет принято по данным пилота.
- На чистом телефоне с включённым режимом разработчика и отладкой по USB каждый проход даёт находки `DEV_OPTIONS` и `ADB_ENABLED`; благодаря ограничению частоты шлюз получает их не чаще раза в сутки.
