# `wolp-device-trust` — справочник по интеграции

Документ для разработчика приложения, которое подключает библиотеку: что вызывать, когда и что делать с результатом. Устройство библиотеки описано в [`ARCHITECTURE.md`](ARCHITECTURE.md), проверки среды выполнения — в [`RASP.md`](RASP.md).

Публичный API — это объект `org.wolpmessenger.devicetrust.DeviceTrust` и пакет `org.wolpmessenger.devicetrust.api`. Остальные классы либо `internal`, либо помечены `@InternalDeviceTrustApi`: без явного opt-in их использование — ошибка компиляции. Они нужны модулю `sample` и тестам, приложению — нет.

Термины, которые встречаются ниже:

| Термин | Значение |
|---|---|
| S1, S2, S3 | приложение, эта библиотека и шлюз. Ссылки вида «S2 §6.3» указывают на разделы спецификаций `specs/S2-device-trust-lib.md` и `specs/S3-gateway.md` в репозитории `android-messenger/docs` |
| Шлюз | сервер, который проверяет аттестацию ключа, выдаёт сертификаты устройствам и пропускает к мессенджеру только запросы с действующим сертификатом |
| Kratos | сервис учётных записей (Ory Kratos). Его cookie сессии подтверждает шлюзу, какой пользователь вошёл в веб-клиент |
| Пароль онбординга | одноразовый пароль, который администратор выдаёт пользователю для регистрации устройства |
| Регистрация (enroll) | первое получение сертификата устройства: ключ в Keystore, аттестация, пароль онбординга |
| Продление (renew) | замена действующего сертификата новым; библиотека делает это сама |
| Восстановление (reattest) | получение нового сертификата после того, как прежний истёк или ответ на продление потерялся |
| RASP | проверки среды выполнения: root, перехватчики, отладчик, подмена подписи |
| BLOCK, REPORT | две реакции на находку RASP. BLOCK стирает ключи и Vault и переводит устройство в `Blocked`. REPORT только отправляет сообщение шлюзу |
| Vault | хранилище секретов сквозного шифрования (E2EE) с ключами в Keystore |
| Закреплённый канал | HTTPS-соединение, в котором библиотека сверяет открытый ключ сервера со списком `serverPins` |

## 2. Инициализация и конфигурация

```kotlin
class WolpApp : Application() {
    override fun onCreate() {
        super.onCreate()
        DeviceTrust.init(this, DeviceTrustConfig(
            enrollBaseUrl = "https://enroll.<host>",
            appBaseUrl = "https://app.<host>",
            serverPins = listOf("sha256/<основной>", "sha256/<запасной>"),
            expectedSigningDigests = listOf("<SHA-256 сертификата подписи, hex>"),
            cookieProvider = { CookieManager.getInstance().getCookie("https://<host>") },
            buildKind = BuildKind.valueOf(BuildConfig.BUILD_KIND),
            raspDryRun = BuildConfig.RASP_DRY_RUN,
        ))
        // единственный подписчик событий на весь процесс, см. раздел 5
        appScope.launch { DeviceTrust.events.collect(::onTrustEvent) }
    }
}
```

Правила вызова `init`:

- Вызывайте его один раз, в `Application.onCreate`, а не в `Activity`: процесс запускается также ради push-уведомлений и фоновых задач библиотеки.
- Вызов быстрый и не блокирует поток. Повторный вызов игнорируется, даже с другой конфигурацией.
- `init` бросает `IllegalArgumentException`, если адрес шлюза не начинается с `https://`; если закреплённых ключей меньше двух или они не в виде `sha256/…`; если приложение не отладочное (не debuggable), а `expectedSigningDigests` пуст; если отпечаток подписи — не SHA-256 в шестнадцатеричном виде (двоеточия и пробелы допустимы).

После `init` библиотека в фоне по порядку: сверяет сохранённое состояние с ключами в Keystore и доводит до конца прерванные операции, выполняет проход RASP, планирует фоновое продление (`RenewWorker`), планирует отправку накопленных оповещений и вызывает `ensureFresh()`. Пока сверка не закончилась, `state` равен `Uninitialized`.

### Поля `DeviceTrustConfig`

| Поле | По умолчанию | Назначение |
|---|---|---|
| `enrollBaseUrl` | — (обязательно) | `https://enroll.<host>` — адрес шлюза для регистрации, восстановления и оповещений |
| `appBaseUrl` | — (обязательно) | `https://app.<host>` — адрес шлюза, который требует клиентский сертификат |
| `serverPins` | — (обязательно) | закреплённые ключи сервера в виде `sha256/<base64 от SHA-256 открытого ключа>`, не меньше двух: основной и запасной. Применяются к обоим адресам |
| `deviceKeyStrongBox` | `false` | создавать ключ устройства в StrongBox; если не получилось, библиотека создаёт его в TEE |
| `maxPatchAgeMonths` | `12` | наибольший возраст обновления безопасности Android (`SECURITY_PATCH`), при котором устройство ещё регистрируется |
| `enrollReplayTtl` | 15 минут | сколько времени после сбоя библиотека повторяет завершение регистрации с тем же запросом. Должно совпадать с параметром шлюза `DEVICES_ENROLL_REPLAY_TTL` |
| `reattestGrace` | 7 суток | сколько времени после истечения сертификата ещё возможно восстановление. Должно совпадать с параметром шлюза `DEVICES_REATTEST_GRACE` |
| `httpTimeouts` | `Timeouts(connect = 10 с, read = 20 с)` | тайм-ауты всех HTTP-клиентов библиотеки |
| `workInterval` | 12 часов | период фонового продления (`RenewWorker`) |
| `cookieProvider` | `{ null }` | возвращает cookie сессии Kratos. Нужна, чтобы повторить завершение регистрации после сбоя и чтобы отправить оповещения, которые нечем подписать (ключа устройства ещё или уже нет). Вызывается в момент отправки |
| `reportRateLimit` | `ReportLimit(perCheckWindow = 24 ч, batch = 20, queue = 100)` | ограничения на сообщения REPORT: одно сообщение на пару (проверка, подробность) за окно; находок в одном сообщении; находок в очереди |
| `expectedSigningDigests` | пустой список | SHA-256 сертификатов подписи приложения в шестнадцатеричном виде. Обязателен, если приложение не отладочное |
| `raspPolicy` | `RaspPolicy.default()` | реакции на находки RASP: `RaspPolicy.default().with(RaspCheck.X, RaspReaction.Y)`. Ослабление реакции в выпускаемой сборке игнорируется |
| `raspIntervalForeground` | 5 минут | период проходов RASP, пока приложение на переднем плане |
| `buildKind` | `BuildKind.RELEASE` | заявленный тип сборки: `RELEASE`, `PILOT` или `DEBUG`. Библиотека перепроверяет его при работе |
| `pilotVersionCode` | `{ it % 100 >= 90 }` | признак пилотного `versionCode` |
| `raspDryRun` | `false` | пробный режим: каждая реакция BLOCK заменяется сообщением REPORT. Работает только в пилотной и отладочной сборках |
| `e2eeRoots` | пустой список | секретные чаты: корневые сертификаты центра, выдающего сертификаты устройств, текстом PEM. Ключ собеседника принимается только с сертификатом устройства от одного из них. В рабочей сборке — только рабочий корень, в тестовой — только тестовый. Пусто вместе с `e2eeIssuers` — секретные чаты выключены; см. [раздел 14](#14-секретные-чаты) |
| `e2eeIssuers` | пустой список | SHA-256 открытого ключа (SPKI, 64 шестнадцатеричные цифры) каждого центра, которому разрешено выдавать сертификаты устройств. Задаётся вместе с `e2eeRoots`: одно без другого — `IllegalArgumentException` в `init` |

## 3. Типы сборок

Библиотека различает три типа сборки (`BuildKind`), потому что от типа зависит, можно ли ослаблять реакции RASP.

- Номер версии строится как `versionCode = MMmmpp`. Значения `pp` от 00 до 89 — продуктовые сборки, от 90 до 99 — пилотные сборки перед следующим выпуском (пилот 10290, затем выпуск 10300). У продуктовой и пилотной сборок один `applicationId`: пилот обновляется до выпуска поверх, без переустановки.
- Действующий тип сборки библиотека определяет сама. Если приложение отладочное, действует заявленный `buildKind`. Если заявлен `PILOT` и `versionCode` пилотный, действует `PILOT`. Во всех остальных случаях действует `RELEASE` — в том числе когда заявлен `DEBUG`, но приложение не отладочное.
- В `RELEASE` ослабление реакций и `raspDryRun` игнорируются.
- Отладочной сборке приложения нужно понизить реакции на `APP_DEBUGGABLE` и `DEBUGGER` до `REPORT`, иначе первый же проход RASP заблокирует устройство. Так делает модуль `sample` (`StandConfig.kt`).
- После пилота шлюз поднимает наименьший допустимый номер версии (`DEVICES_MIN_APP_VERSION_CODE`) до первого выпуска, и пилотные сборки перестают получать сертификаты.

Модуль `pilot/` — образец того, как собирать приложение. В нём два варианта одного приложения: `product` (`RELEASE`, пробный режим невозможен) и `pilot` (`PILOT`, пробный режим включён), оба с R8 и release-подписью. Перед каждой release-сборкой задача `verify<Variant>BuildKind` отказывает, если тип сборки не соответствует варианту, `versionCode` не в своём диапазоне, пробный режим включён в продуктовой сборке, release-сборка отладочная, подпись не настроена или её отпечатка нет в `expectedSigningDigests`. Сборочная система приложения должна повторять эту проверку.

## 4. Состояние

`DeviceTrust.state` — `StateFlow<TrustState>`. Приложение выбирает экран по его значению. Состояние пересчитывается по времени библиотеки, а не по часам телефона.

| `TrustState` | Что означает | Что делает приложение |
|---|---|---|
| `Uninitialized` | `init` не вызван или сверка после него ещё идёт | показывает заставку |
| `NotEnrolled` | устройство не зарегистрировано | вызывает `precheck()` и показывает экран регистрации |
| `Active(notAfter, renewAfter)` | сертификат действует | открывает мессенджер |
| `RenewalDue(notAfter)` | пора продлевать, сертификат ещё действует | то же, что при `Active`; продление идёт само |
| `ExpiredGrace(graceUntil)` | сертификат истёк, восстановление ещё возможно | вызывает `ensureFresh()`; мессенджер недоступен, шлюз запросы не пропустит |
| `ReEnrollRequired` | восстановление невозможно. Vault сохранён | показывает повторную регистрацию; нужен новый пароль онбординга от администратора |
| `UpdateRequired(kind, reason)` | шлюз требует обновить приложение (`UpdateKind.APP`) или систему (`UpdateKind.OS`). Ключи сохранены | показывает экран обновления; файлы обновления загружает через `updateHttpClient()` |
| `Blocked(reason)` | конечное состояние: ключи и Vault стёрты. Выйти из него можно только удалением данных приложения или переустановкой | показывает экран блокировки с текстом по `BlockReason`: `RASP`, `REVOKED`, `REPLACED`, `IDENTITY_REVOKED`, `POLICY` |

В состояниях `ExpiredGrace`, `ReEnrollRequired`, `UpdateRequired`, `NotEnrolled` и `Blocked` `clientCredentials()` возвращает `null`, и `okHttpClient()` не предъявляет клиентский сертификат.

Состояние `UpdateRequired` снимается само, когда изменился `versionCode` приложения или дата обновления безопасности системы: библиотека проверяет это при запуске и при каждом `ensureFresh()`.

`DeviceTrust.credentialsVersion` — `StateFlow<Long>`, счётчик, который растёт при каждой смене ключа или сертификата и при удалении ключей. При каждом его изменении приложение обязано пересоздать всё, что держит клиентский сертификат; для WebView это вызов `WebView.clearClientCertPreferences`. Счётчик — состояние, а не событие, поэтому пропустить изменение нельзя.

`DeviceTrust.trustNow()` возвращает время сервера (`Instant`) или `null`. `null` означает, что после перезагрузки телефона ещё не было ни одного ответа шлюза; до тех пор приложению остаются системные часы.

## 5. События

`DeviceTrust.events` — `Flow<TrustEvent>`. События накапливаются, пока их не заберут (до 64, при переполнении пропадают самые старые), и каждое доставляется один раз. Поэтому подписчик должен быть ровно один на процесс — в `Application.onCreate`, сразу после `init`. Событие, возникшее до подписки, не теряется.

| Событие | Когда возникает | Что делает приложение |
|---|---|---|
| `TrustEvent.Blocked(reason)` | при переходе в `Blocked` и при каждом запуске в этом состоянии | стирает свои данные: хранилище WebView, cookie, токен push. Событие повторяется, поэтому действие должно быть безопасным при повторе |
| `TrustEvent.VaultReset` | при запуске библиотека обнаружила, что ключей Vault нет или их набор неполон, и создала новые. Так бывает, в частности, после снятия блокировки экрана | очищает данные сквозного шифрования веб-клиента, сбрасывает ключ push и кэш имён, регистрирует push заново. Всё, что было зашифровано прежними ключами, больше не расшифруется |
| `TrustEvent.BackgroundKeysReset` | один раз на устройстве, где Vault был создан прежней версией библиотеки: ключи для назначений `NAMES` и `PUSH_KEY` заменены, данные `E2EE` и `E2EE_PLAINTEXT` целы | сбрасывает только ключ push и кэш имён и регистрирует push заново. Данные сквозного шифрования не трогает |

`TrustEvent` — `sealed interface`: выражение `when` без ветки `else` должно перечислять все три события.

## 6. Вызовы

Все `suspend`-функции `DeviceTrust` можно вызывать из главного потока: работа выполняется на `Dispatchers.IO`. Вызовы потокобезопасны; одновременные `ensureFresh()` выполняются по очереди, и второй находит сертификат уже свежим.

До `init`: `suspend`-функции, `okHttpClient()`, `updateHttpClient()` и `vault` бросают `IllegalStateException`; `state` равен `Uninitialized`, `credentialsVersion` равен 0; `clientCredentials()`, `trustNow()` и `deviceInfo()` возвращают `null`.

| Член `DeviceTrust` | Когда вызывать | Результат |
|---|---|---|
| `init(context, config)` | один раз в `Application.onCreate` | см. [раздел 2](#2-инициализация-и-конфигурация) |
| `state`, `credentialsVersion`, `trustNow()` | постоянно наблюдать | см. [раздел 4](#4-состояние) |
| `events` | один подписчик на процесс | см. [раздел 5](#5-события) |
| `suspend precheck(): PrecheckResult` | перед экраном регистрации | см. [«Результат `precheck`»](#результат-precheck) |
| `suspend enroll(kratosCookie, onboardingPassword: CharArray): EnrollResult` | пользователь ввёл пароль онбординга | см. [«Результат `enroll`»](#результат-enroll). Массив с паролем обнуляется при возврате |
| `suspend ensureFresh(): TrustState` | при запуске, в `onResume` и когда ответ шлюза содержит заголовок `X-Device-Renew: 1` | новое состояние. Продлевает сертификат в `RenewalDue`, восстанавливает в `ExpiredGrace`, в остальных состояниях ничего не делает |
| `suspend onGatewayDenied(code, source, reason = null): TrustState` | шлюз ответил отказом | новое состояние; см. [раздел 7](#7-коды-шлюза) |
| `suspend checkSessionBinding(kratosCookie): SessionBinding` | шлюз ответил `USER_MISMATCH` | `Match` — сессия принадлежит владельцу устройства. `Mismatch` — подтверждено по закреплённому каналу, что нет: приложение выходит из Kratos и показывает «обратитесь к администратору». `NoSession` — сессии нет. `Failed(cause, code)` — проверить не удалось: `NO_CREDENTIALS` (нет действующего сертификата), `NETWORK`, `DENIED` (шлюз отказал самому устройству; код уже обработан библиотекой). Отвязку устройства пользователю не предлагать |
| `suspend checkIntegrity(): RaspReport` | по желанию; библиотека и так запускает RASP сама | отчёт о проходе; реакции уже выполнены. См. [раздел 10](#10-rasp-с-точки-зрения-приложения) |
| `suspend unenroll(): UnenrollResult` | смена пользователя на устройстве. В первой версии приложения пользователю не предлагается | `Ok(ServerNotice.PENDING)` — подписанное уведомление шлюзу поставлено в очередь; `Ok(ServerNotice.NOT_NEEDED)` — ключа устройства нет, уведомлять нечем и незачем. Локально отвязка завершается всегда: удаляются ключи устройства, сертификаты и Vault. В `Blocked` вызов ничего не меняет |
| `clientCredentials(): ClientCredentials?` | в `WebViewClient.onReceivedClientCertRequest` | закрытый ключ (ссылка на ключ в Keystore, байтов ключа нет) и цепочка `[сертификат устройства, промежуточный]`; `null`, если действующего сертификата нет |
| `okHttpClient(): OkHttpClient` | для всех запросов к шлюзу, кроме обновлений | см. [раздел 8](#8-сеть-и-webview) |
| `updateHttpClient(): OkHttpClient` | только для загрузки обновлений | см. [раздел 8](#8-сеть-и-webview) |
| `vault: Vault` | шифрование секретов | см. [раздел 9](#9-vault) |
| `e2ee: E2ee` | секретные чаты: шесть операций для моста | см. [раздел 14](#14-секретные-чаты). Без `e2eeRoots` и `e2eeIssuers` — `IllegalStateException` |
| `deviceInfo(): DeviceSecurityInfo?` | диагностика | сведения последнего вызова `precheck()`, завершившегося `Supported` или `Unsupported`; до первого такого вызова — `null` |

### Результат `precheck`

| `PrecheckResult` | Что означает | Что делает приложение |
|---|---|---|
| `Supported(info, reports)` | устройство подходит; `reports` — находки RASP с реакцией REPORT | показывает экран регистрации |
| `Unsupported(reasons, info)` | устройство не подходит; шлюзу ничего не отправлялось | показывает экран «устройство не поддерживается» с текстом по каждой причине |
| `Compromised(report)` | RASP нашёл блокирующий признак; реакция BLOCK уже выполнена | состояние уже `Blocked` — показывает экран блокировки |

Причины `UnsupportedReason`:

| Причина | Что означает | Текст для пользователя |
|---|---|---|
| `SOFTWARE_KEYSTORE` | ключи Keystore не защищены аппаратно | устройство не поддерживается |
| `PATCH_TOO_OLD` | обновление безопасности старше `maxPatchAgeMonths` или дата не читается | обновите систему |
| `NO_SCREEN_LOCK` | не установлены PIN, графический ключ или пароль. Ключ секретов E2EE привязан к блокировке экрана, поэтому без неё регистрация невозможна | установите блокировку экрана и откройте приложение снова; уместна кнопка, открывающая `Settings.ACTION_SECURITY_SETTINGS` |

### Результат `enroll`

| `EnrollResult` | Что означает | Что делает приложение |
|---|---|---|
| `Ok(deviceId)` | устройство зарегистрировано, состояние `Active` | открывает мессенджер |
| `WrongPassword(attemptsLeft)` | пароль неверен; `attemptsLeft` всегда не меньше 1 | просит ввести пароль снова |
| `PasswordBurned` | попытки исчерпаны, пароль погашен | просит обратиться к администратору за новым паролем |
| `PasswordExpired` | срок пароля истёк | то же |
| `NoPassword` | для пользователя пароль не выдан | то же |
| `NoSession` | нет сессии Kratos | выполняет вход в Kratos заново и повторяет |
| `PolicyRejected(reason)` | шлюз отклонил устройство по политике аттестации | показывает отказ с причиной |
| `UpdateRequired(kind)` | нужно обновить приложение (`APP`) или систему (`OS`). Пароль при этом не израсходован | показывает экран обновления |
| `Unsupported(reasons)` | предпроверка не прошла; `reasons` — имена `UnsupportedReason` | показывает экран «устройство не поддерживается» |
| `Blocked(reason)` | устройство уже было заблокировано, либо RASP заблокировал его сейчас (`RASP`), либо шлюз сообщил, что учётная запись пользователя отозвана (`IDENTITY_REVOKED`). В последнем случае библиотека ничего не стирает и `state` не меняется | показывает экран блокировки с текстом по причине |
| `Transient(cause, retryAfter)` | временный сбой: сеть, перегрузка шлюза, вызов в неподходящем состоянии | повторяет позже; если `retryAfter` задан — не раньше |

## 7. Коды шлюза

Шлюз сообщает причину отказа заголовком ответа `X-Device-Deny` или телом `{"error":"<КОД>"}`. Приложение превращает строку в `GatewayCode` вызовом `GatewayCode.parse(строка)` (неизвестная строка даёт `UNKNOWN`) и передаёт код в `onGatewayDenied`, указав источник:

| `DenySource` | Когда указывать | Как действует библиотека |
|---|---|---|
| `PINNED_CLIENT` | отказ пришёл в ответе на запрос через `okHttpClient()` | выполняет действие по таблице ниже |
| `WEBVIEW` | отказ увидел WebView | сам код ничего не удаляет. Не чаще раза в 30 секунд библиотека отправляет `GET /v1/device/ping` по закреплённому каналу и действует по коду из ответа на этот запрос. Если запрос не удался (нет сети, ключ сервера не совпал с закреплённым), ничего не меняется. Если действующего сертификата нет, вместо запроса выполняется `ensureFresh()` |

Параметр `reason` передаётся только для `UPDATE_REQUIRED`: это поле `reason` из тела ответа. Значение `APP_VERSION_TOO_OLD` даёт `UpdateKind.APP`, любое другое — `UpdateKind.OS`.

Действия по кодам, полученным по закреплённому каналу:

| Код | Действие библиотеки |
|---|---|
| `NO_SESSION` | ничего. Приложение само выполняет вход в Kratos заново |
| `USER_MISMATCH` | ничего. Приложение вызывает `checkSessionBinding` |
| `CERT_INVALID`, `CERT_UNKNOWN`, `CERT_EXPIRED` | `ensureFresh()` |
| `CERT_SUPERSEDED` | восстановление: ответ на продление был потерян, а шлюз уже выдал следующий сертификат |
| `UPDATE_REQUIRED` | переход в `UpdateRequired` |
| `DEVICE_REVOKED`, `DEVICE_REPLACED`, `IDENTITY_REVOKED`, `DEVICE_POLICY` | BLOCK без сообщения шлюзу; причина блокировки — `REVOKED`, `REPLACED`, `IDENTITY_REVOKED`, `POLICY` соответственно |
| `REATTEST_NOT_ALLOWED` | если сертификат истёк — удаление ключей устройства и переход в `ReEnrollRequired`; если ещё действует — ничего |
| `RATE_LIMITED`, `NONCE_INVALID`, `UNKNOWN` и коды регистрации (`NO_PASSWORD`, `PASSWORD_EXPIRED`, `PASSWORD_BURNED`, `WRONG_PASSWORD`, `CSR_INVALID`, `POLICY_REJECTED`) | ничего |

Коды `NO_SESSION`, `USER_MISMATCH`, `RATE_LIMITED` и `UNKNOWN` с источником `WEBVIEW` не запускают и проверочный запрос. В состоянии `Blocked` любые коды игнорируются. У незарегистрированного устройства (`NotEnrolled`) действуют только четыре кода блокировки.

## 8. Сеть и WebView

| Член | Для чего | Свойства |
|---|---|---|
| `okHttpClient()` | все запросы к шлюзу, кроме обновлений | Предъявляет клиентский сертификат устройства и закрепляет ключи сервера для обоих адресов шлюза. Сертификат выбирается в момент установления TLS-соединения. При изменении `credentialsVersion` библиотека закрывает свободные соединения и сбрасывает сохранённые TLS-сессии, поэтому новые соединения идут с новым сертификатом. Если отказ пришёл по соединению, установленному с прежним сертификатом, клиент сам один раз повторяет запрос с текущим. Не следует за перенаправлениями |
| `updateHttpClient()` | только описание обновления и файл APK | Доверяет системным центрам сертификации; ключи сервера не закрепляет и клиентский сертификат не предъявляет. Так ошибка при смене ключа сервера не лишит приложение обновления, которое её исправляет. Целостность обновления приложение проверяет само |
| `clientCredentials()` | клиентский сертификат для WebView | см. ниже |

В `WebViewClient.onReceivedClientCertRequest`:

```kotlin
val creds = DeviceTrust.clientCredentials()
if (creds != null) request.proceed(creds.privateKey, creds.chain) else request.ignore()
```

Если сертификата нет, вызывайте `request.ignore()`, а не `request.cancel()`: WebView запоминает решения `proceed` и `cancel` до вызова `clearClientCertPreferences`, а `ignore` не запоминает.

## 9. Vault

`DeviceTrust.vault` шифрует секреты приложения ключами, которые хранятся в Keystore и не покидают его:

```kotlin
val blob = DeviceTrust.vault.wrap(plain, VaultPurpose.E2EE)
val plain = DeviceTrust.vault.unwrap(blob, VaultPurpose.E2EE)
```

Обе функции — `suspend`; необязательный третий параметр `extraAad` привязывает блоб к дополнительным данным, и при расшифровке их нужно передать такими же. Назначение (`VaultPurpose`) входит в проверяемые данные: блоб одного назначения не расшифруется как блоб другого.

| Назначение | Доступно при заблокированном экране | Для чего |
|---|---|---|
| `E2EE`, `E2EE_PLAINTEXT` | нет | секреты сквозного шифрования. Только эти два назначения должны быть доступны коду веб-клиента |
| `NAMES`, `PUSH_KEY` | да, после первой разблокировки телефона с момента перезагрузки | кэш имён и ключ для push: обработка уведомления работает за экраном блокировки |

Ключ назначений `E2EE` и `E2EE_PLAINTEXT` удаляется из памяти процесса при выключении экрана и загружается снова при следующем обращении с разблокированным экраном.

Перед каждой операцией Vault ждёт завершения первого прохода RASP в этом процессе — обычно доли секунды после `init`, не дольше 20 секунд.

### Ошибки `VaultException`

| Ошибка | Когда возникает | Что делает приложение |
|---|---|---|
| `Locked` | Временная недоступность, ничего не потеряно: (1) телефон ещё не разблокировали после перезагрузки; (2) экран заблокирован — только для `E2EE` и `E2EE_PLAINTEXT`; (3) первый проход RASP процесса ещё не закончился за 20 секунд; (4) последний проход RASP нашёл блокирующий признак или не смог выполниться; (5) в выпускаемой сборке не отработала native-часть RASP | повторяет операцию позже, когда приложение на переднем плане и экран разблокирован. **Данные не очищает** |
| `KeyGone` | Ключей нет, и зашифрованное ими не восстановить: ключи ещё не созданы (устройство не зарегистрировано); уничтожены реакцией BLOCK или отвязкой; повреждён файл ключа; для `E2EE` и `E2EE_PLAINTEXT` — на телефоне сняли блокировку экрана | считает данные этого назначения потерянными и начинает заново. После снятия блокировки экрана при следующем запуске с установленной блокировкой придёт `VaultReset` |
| `Corrupt` | Блоб не расшифровывается: он повреждён или короче наименьшей длины, начинается не с байта `0x02`, зашифрован для другого назначения, с другим `extraAad` или прежними ключами (до `VaultReset` или `BackgroundKeysReset`) | считает этот блоб потерянным |

## 10. RASP с точки зрения приложения

Библиотека сама запускает проход RASP: после `init`, при выходе приложения на передний план и затем каждые `raspIntervalForeground`, внутри `precheck()` и `enroll()`, перед каждым продлением и восстановлением. Вызывать `checkIntegrity()` приложению не обязательно.

Что приложению нужно знать:

- Находка с реакцией BLOCK приводит к тому же, что отзыв устройства: ключи и Vault стёрты, состояние `Blocked(RASP)`, приходит событие `Blocked`. Отменить это нельзя.
- Находки с реакцией REPORT уходят шлюзу сами и ничего не меняют для пользователя.
- Пока проход не дал чистого результата, Vault отвечает `VaultException.Locked` (см. [раздел 9](#9-vault)).
- `checkIntegrity()` возвращает `RaspReport`: `findings` — все находки, `blocking` и `reports` — они же по реакциям. Каждая находка — `RaspFinding(id, reaction, detail)`; идентификаторы перечислены в `RaspCheck`, реакции по умолчанию — в `RaspCheck.DEFAULTS`.
- Реакции настраиваются через `raspPolicy`, пробный режим — через `raspDryRun`; оба ослабления работают только в пилотной и отладочной сборках.

Полный перечень проверок, порядок реакции BLOCK и ограничения частоты сообщений — в [`RASP.md`](RASP.md).

## 11. Чего библиотека не делает

- Не показывает интерфейс.
- Не предоставляет мост для JavaScript: его пишет приложение и само следит, чтобы веб-клиенту были доступны только назначения `E2EE` и `E2EE_PLAINTEXT`.
- Не работает с push-уведомлениями и не содержит Firebase.
- Не загружает и не устанавливает обновления; только даёт для этого `updateHttpClient()`.
- Не хранит данные веб-клиента.
- Не пишет в журнал пароли, cookie, одноразовые числа, ключи. Журнал библиотеки — logcat с тегом `DeviceTrust`: только названия событий, коды и состояния.

## 12. Диагностика неполадок

| Признак | Причина | Что делать |
|---|---|---|
| `init` бросает `IllegalArgumentException` | не `https`-адрес; меньше двух закреплённых ключей или неверный их вид; пустой или неверный `expectedSigningDigests` в неотладочной сборке | исправить конфигурацию; текст исключения называет поле |
| `IllegalStateException: DeviceTrust.init() was not called` | вызов до `init`, например из `Activity` процесса, где `Application.onCreate` его не выполнил | вызывать `init` в `Application.onCreate` |
| `state` долго остаётся `Uninitialized` | сверка при запуске ещё идёт: она может обращаться к шлюзу, чтобы завершить прерванную регистрацию | дождаться; искать в logcat по тегу `DeviceTrust` запись `init_step_failed` |
| Отладочная сборка сразу переходит в `Blocked(RASP)` | проверки `APP_DEBUGGABLE` и `DEBUGGER` по умолчанию блокируют | понизить обе до `REPORT` в `raspPolicy` и передать `buildKind = BuildKind.DEBUG`; удалить данные приложения, чтобы выйти из `Blocked` |
| Выпускаемая сборка блокируется с находкой `APK_SIGNATURE` | в `expectedSigningDigests` нет отпечатка сертификата, которым подписан установленный APK | передать SHA-256 сертификата release-ключа; проверять это при сборке, как `verify<Variant>BuildKind` |
| Понижение реакции или `raspDryRun` не действуют | действующий тип сборки — `RELEASE`: приложение не отладочное и либо заявлен не `PILOT`, либо `versionCode` не пилотный. В logcat — `rasp_policy_downgrade_ignored` | использовать пилотный `versionCode` и `buildKind = PILOT` |
| `precheck()` возвращает `Unsupported([SOFTWARE_KEYSTORE])` | эмулятор или устройство без аппаратного Keystore | для разработки использовать реальное устройство |
| `precheck()` возвращает `Unsupported([NO_SCREEN_LOCK])` | не установлена блокировка экрана | попросить пользователя установить PIN, графический ключ или пароль |
| `enroll()` возвращает `Transient` с причиной `IllegalStateException: enroll is not allowed in ENROLLED` | устройство уже зарегистрировано. То же самое приходит, когда `state` показывает `ReEnrollRequired` по одним часам телефона, а шлюз ещё не подтвердил, что восстановление невозможно: перед регистрацией библиотека спрашивает шлюз, и без сети ответа нет | в первом случае регистрация не нужна. Во втором — повторить `enroll()` при наличии сети: после отказа шлюза в восстановлении регистрация проходит, Vault сохраняется. Если шлюз вместо отказа восстановил сертификат (часы телефона ошибались), `state` станет `Active` и регистрация не нужна |
| Операции Vault бросают `Locked` сразу после запуска | первый проход RASP ещё не закончился | повторить; ждать дольше 20 секунд не придётся |
| Операции `E2EE` бросают `Locked` в фоне | экран заблокирован | не обращаться к `E2EE` и `E2EE_PLAINTEXT` за экраном блокировки; для фоновой работы есть `NAMES` и `PUSH_KEY` |
| Операции Vault бросают `Locked` постоянно, устройство не заблокировано | в выпускаемой сборке не загрузилась `libwolpdt.so` или её ответ не прошёл проверку; в отчёте `checkIntegrity()` есть `HOOK_TAMPER` | проверить, что `.so` попала в APK для архитектуры устройства и что R8 не удалил класс `NativeRasp` (правила библиотеки должны применяться) |
| WebView продолжает предъявлять старый сертификат или не предъявляет никакого | не вызван `clearClientCertPreferences` после изменения `credentialsVersion`, либо на запрос сертификата ответили `cancel()` | наблюдать `credentialsVersion`; при отсутствии сертификата отвечать `ignore()` |
| Событие `Blocked` приходит при каждом запуске | так задумано: блокировка могла произойти, когда интерфейса не было | сделать очистку данных безопасной при повторе |
| События приходят не все | подписчиков на `events` больше одного: каждое событие получает только один из них | оставить одного подписчика на процесс |
| Сертификат не продлевается в фоне | WorkManager откладывает задачи редко используемых приложений | вызывать `ensureFresh()` при запуске и в `onResume`; после истечения сертификата в течение `reattestGrace` сработает восстановление |

## 13. Переход с предыдущей версии

Раздел перечисляет, что должно измениться в приложении, которое работало с версией библиотеки до двухключевого Vault и обязательной блокировки экрана.

| Что изменилось в библиотеке | Что сделать в приложении |
|---|---|
| Появилось событие `TrustEvent.BackgroundKeysReset` | Добавить ветку в обработчик событий: сбросить ключ push и кэш имён, зарегистрировать push заново. Данные сквозного шифрования не очищать. Без этой ветки `when` по `TrustEvent` без `else` не скомпилируется |
| Назначения `E2EE` и `E2EE_PLAINTEXT` доступны только при разблокированном экране | Не обращаться к ним в коде, который работает за экраном блокировки (обработка push). Для `VaultException.Locked` сделать повтор после разблокировки |
| `VaultException.Locked` возникает в новых случаях: экран заблокирован, проход RASP не закончен или не чист | Убедиться, что ни один обработчик `Locked` не очищает данные: эта ошибка не означает потерю ключей |
| `precheck()` возвращает новую причину `UnsupportedReason.NO_SCREEN_LOCK` | Добавить текст «установите блокировку экрана» на всех языках приложения |
| Снятие блокировки экрана на зарегистрированном устройстве уничтожает ключи `E2EE` | Отдельного кода не нужно: сработают существующие обработчики `KeyGone` и `VaultReset`. Проверить на устройстве |
| Появился идентификатор проверки `RaspCheck.ROOT_TEST_KEYS` с реакцией REPORT; признак `test-keys` больше не блокирует | Ничего, если приложение не переопределяло реакцию на `ROOT_PROPS` ради этого признака |
| Блокирующая находка эвристической проверки подтверждается вторым проходом; неподтверждённая уходит как REPORT | Ничего |
| Повреждённый файл состояния больше не приводит к падению при запуске: устройство становится `NotEnrolled` | Ничего; пользователю понадобится новая регистрация |
| Библиотека отправляет шлюзу сводку RASP при продлении и восстановлении | Ничего. Отправка начинается, когда поддержку объявит шлюз |

Vault прежней версии переносится сам: при запуске и при выходе приложения на передний план, когда телефон разблокирован и блокировка экрана установлена. До переноса он работает по-прежнему, после переноса приходит `BackgroundKeysReset`.

## 14. Секретные чаты

Ключи секретных чатов и шифрование живут в библиотеке (`libsignal`). Приложение получает семь операций и ни одного ключа; их оно отдаёт веб-клиенту через свой мост. Спецификация — [specs/002](../specs/002-secret-chat-crypto/spec.md).

```kotlin
val envelope = DeviceTrust.e2ee.encrypt(peer, text)      // "E2EE2:…" — в тело сообщения
val text = DeviceTrust.e2ee.decrypt(peer, envelope)
```

`peer` — учётная запись собеседника (идентификатор Kratos). Своя учётная запись берётся из сертификата устройства.

| Операция `DeviceTrust.e2ee` | Что делает |
|---|---|
| `suspend encrypt(peer, text): String` | шифрует; первое сообщение собеседнику берёт его ключи в службе ключей и проверяет паспорт |
| `suspend decrypt(peer, envelope): String` | расшифровывает; то же сообщение второй раз — отказ `duplicate` |
| `suspend peerState(peer): E2eePeerState` | состояние собеседника (`unverified`, `passport`, `verified`, `reverify`) и признак «ключ сменился». Чтение снимает признак |
| `suspend safetyNumber(peer): String?` | 60 цифр для сверки; `null`, пока ключ собеседника не принят |
| `suspend setVerified(peer, verified)` | пользователь сверил код или снял отметку |
| `suspend resetSession(peer)` | восстановление сообщений: следующее шифрование строит новую сессию. Вызывать по запросу восстановления, не чаще раза в 10 секунд на собеседника |
| `suspend wipe()` | выход из учётной записи: стирает ключи, сессии, запомненные ключи собеседников и отметки; убирает запись из службы ключей, если она отвечает за 4 секунды. Не отказывает и не ждёт разблокировки экрана. Вызывать, пока сессия ещё действует. До входа в другую сессию библиотека ничего не публикует; после входа создаёт новый ключ — собеседники увидят смену ключа |

Все операции можно вызывать из главного потока. Отказ — `E2eeException`; в `failure.code` причина из закрытого списка, её мост передаёт веб-клиенту как есть:

| Код | Когда | Что делать |
|---|---|---|
| `locked` | экран заблокирован или проход RASP не чист | повторить после разблокировки; ничего не потеряно |
| `not_enrolled` | нет сертификата устройства или ключа хранилища | ждать регистрации |
| `no_network` | служба ключей не ответила, а сессии с собеседником ещё нет | повторить позже |
| `no_device` | у собеседника нет записи в службе ключей; также шифрование самому себе | сообщить пользователю |
| `no_passport` | ключ собеседника опубликован без паспорта — он не в приложении | сообщить пользователю |
| `bad_passport` | паспорт или ключи собеседника не прошли проверку; на шлюз ушло оповещение | сообщение не отправлять |
| `reverify` | сверенный по коду собеседник сменил ключ | сверить заново или снять отметку |
| `multi_device` | служба ключей вернула больше одного устройства | сообщение не отправлять |
| `duplicate` | сообщение уже расшифровано | пропустить |
| `undecryptable` | сообщение не расшифровать | запросить у отправителя восстановление |

Что библиотека делает сама, без участия приложения:

- **Публикует свои ключи в службе ключей** (`<appBaseUrl>/key-directory/v1/…`) по каналу с сертификатом устройства и закреплённым ключом сервера, с cookie из `cookieProvider`. Без cookie служба отвечает отказом, и публикация повторяется позже.
- **Подписывает паспорт** — ключ устройства в Keystore подписывает ключ мессенджера. Паспорт уходит с каждой публикацией и обновляется после продления сертификата.
- **Пополняет одноразовые ключи**: осталось меньше 20 — до 100. **Меняет подписанный и постквантовый ключ** раз в двое суток; прежние расшифровывают ещё 30 суток.
- **Сверяет свою запись** при запуске, после продления сертификата и раз в час, пока приложение на переднем плане. Чужой ключ в своей записи — оповещение на шлюз и повторная публикация.
- **Сообщает на шлюз** по каналу оповещений (REPORT): `E2EE_BAD_PASSPORT` с причиной и учётной записью собеседника, `E2EE_FOREIGN_KEY`.

Публикация требует разблокированного экрана и зарегистрированного устройства; до этого она откладывается. Неудачи видны в журнале: `e2ee_sync_failed <код>`.

Требования к сборке приложения — в [разделе 1](#1-подключение), строка `libsignal`.
